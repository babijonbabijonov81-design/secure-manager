# Модель безопасности Veil

В этом документе описано, как Veil защищает переписку, какие у него есть ограничения и где в коде лежит каждая часть.

## Криптографические примитивы

Все примитивы берутся из библиотек [noble](https://paulmillr.com/noble/): они написаны на чистом JavaScript, не имеют зависимостей и прошли независимый аудит.

| Назначение | Алгоритм |
| --- | --- |
| Согласование ключей | X25519 |
| Подписи | Ed25519 |
| Вывод ключей | HKDF-SHA256, HMAC-SHA256 |
| Шифрование с аутентификацией | XChaCha20-Poly1305 (192-битный случайный nonce) |
| Ключ из пароля | scrypt (N = 2¹⁷, r = 8, p = 1, 128 МиБ) |
| Код безопасности | SHA-512, 5200 итераций |

Код: [`src/core/crypto/primitives.ts`](../src/core/crypto/primitives.ts).

## Ключи пользователя

- **Ключ личности (Ed25519).** Это публичный идентификатор аккаунта (`userId`). Он подписывает остальные ключи.
- **Ключ DH личности (X25519).** Подписан ключом личности.
- **Подписанный предключ (SPK, X25519).** Меняется раз в неделю. Три последних хранятся, чтобы можно было прочитать задержавшиеся первые сообщения.
- **Одноразовые предключи (OPK, X25519).** Сервер держит пачку из 100 штук и выдаёт каждый только один раз. Приватный ключ уничтожается сразу после использования.

Сервер проверяет подписи при регистрации, а клиент проверяет их ещё раз при получении. Поэтому сервер не может незаметно подложить свой ключ: для этого ему пришлось бы подделать подпись Ed25519.

## Установка сеанса: X3DH

[`src/core/crypto/x3dh.ts`](../src/core/crypto/x3dh.ts) реализует [спецификацию Signal](https://signal.org/docs/specifications/x3dh/):

```
DH1 = DH(IK_A, SPK_B)   DH2 = DH(EK_A, IK_B)   DH3 = DH(EK_A, SPK_B)   DH4 = DH(EK_A, OPK_B)
SK  = HKDF(0xFF×32 ‖ DH1 ‖ DH2 ‖ DH3 ‖ DH4)
AD  = IK_A(sign) ‖ IK_A(dh) ‖ IK_B(sign) ‖ IK_B(dh)
```

Пока собеседник не ответит, каждое сообщение инициатора несёт заголовок X3DH. Так сеанс можно установить по любому первому дошедшему сообщению, даже если они пришли не по порядку.

## Шифрование сообщений: Double Ratchet

[`src/core/crypto/ratchet.ts`](../src/core/crypto/ratchet.ts) реализует [спецификацию Signal](https://signal.org/docs/specifications/doubleratchet/):

- у каждого сообщения свой ключ, выведенный из цепочки HMAC. Использованные ключи стираются, и это даёт **прямую секретность**;
- каждый ответ подмешивает новый обмен DH, и это даёт **восстановление после компрометации**;
- сообщения, пришедшие не по порядку, обрабатываются корректно: пропущено может быть не больше 1000 сообщений подряд и не больше 2000 в сумме;
- заголовок (`dh`, `pn`, `n`) входит в AEAD как связанные данные;
- encrypt и decrypt не изменяют входное состояние, поэтому подделанное сообщение не может испортить сеанс.

Если оба собеседника начали переписку одновременно, у каждого появится по два сеанса. Сеанс, на котором последнее сообщение успешно расшифровалось, становится текущим, и стороны сходятся к одному сеансу (это проверяет тест).

Состояние сеанса записывается на диск **до** того, как шифротекст покидает устройство. Иначе после сбоя могли бы повторно использоваться ключи.

## Конверт: sealed sender и выравнивание

[`src/core/crypto/sealed.ts`](../src/core/crypto/sealed.ts). Сообщение Double Ratchet вместе с идентификатором отправителя шифруется ещё раз, на ключ DH личности получателя с одноразовым эфемерным ключом:

```
key = HKDF(DH(e, IK_B), salt = e ‖ IK_B, "Veil-Sealed-v1")
envelope = { e, nonce, XChaCha20-Poly1305(key, pad(sender ‖ ratchet message)) }
```

- Отправитель спрятан внутри конверта. Подлинность отправителя получатель проверяет криптографически: подпись его ключа DH плюс то, что ключи личности входят в AD сеанса.
- **Доставка без входа.** Одного шифрования мало: если конверт уходит по соединению, на котором вы вошли в аккаунт, сервер видит пару «кто → кому». Поэтому у каждого аккаунта есть **ключ доставки** — 16 случайных байт. Контакты получают его внутри зашифрованных сообщений (`p.ak` в сообщении, `ak` в профиле), сервер хранит только SHA-256 от него (`access_set`). Конверты контакту с ключом уходят по **второму соединению, которое никогда не входит в аккаунт** (`send_sealed`, [`src/core/relay-client.ts`](../src/core/relay-client.ts) `SealedSender`): сервер проверяет ключ и видит получателя, но не отправителя. На «нет такого пользователя» и «неверный ключ» он отвечает одинаково. Анонимные отправки ограничены по IP и по получателю.
- **Где отправитель всё же виден.** Первое сообщение незнакомцу (ключа доставки у вас ещё нет), служебные запросы (поиск по @имени, предключи, резервная копия) и сообщения собеседникам на старых версиях идут из аккаунта. Оба соединения идут с одного IP-адреса, так что по адресу и времени их можно сопоставить; от этого защищают VPN или Tor. Так же устроено и у Signal.
- **Блокировка.** Заблокированный человек знает ваш старый ключ доставки, поэтому при блокировке Veil создаёт новый, сообщает серверу его хэш и рассылает сам ключ остальным контактам внутри шифра.
- Длина данных выравнивается по схеме **Padmé**: накладные расходы не больше 12%, а наружу утекает O(log log L) бит информации о длине.
- Индикатор набора текста и статус «в сети» шифруются отдельным ключом сеанса и не продвигают ratchet. Если сервер их отбросит (собеседник не в сети), рассинхронизации не будет.

## Реакции, ответы, удаление и статус «в сети»

Всё это обычные зашифрованные сообщения внутри сеанса, сервер не отличает их от текста:

- **реакция** ссылается на идентификатор сообщения и передаёт эмодзи;
- **ответ** несёт идентификатор и короткую цитату исходного сообщения;
- **удаление** стирает сообщение у обоих собеседников вместе с цитатами на него. Никакой заглушки «сообщение удалено» не остаётся. Удалить его на устройстве собеседника принудительно невозможно в принципе (у него может быть изменённая программа), но обычный Veil выполняет просьбу сразу;
- **«в сети»** — эфемерный сигнал, который отправляется только контактам: при входе, раз в минуту, пока собеседник тоже в сети, и при выходе. Сервер не ведёт журнал присутствия. Если выбрать «был(а) недавно», вместо статуса уходит сигнал `hidden` без времени;
- **стикеры** передаются как обычные зашифрованные вложения. Сохранённый стикер получает идентификатор из SHA-256 содержимого.

## Ретранслятор

[`server/src/relay.ts`](../server/src/relay.ts):

- вход по подписи Ed25519 под одноразовым nonce соединения;
- хранит только `username`, публичные ключи и очереди непрочитанных конвертов. Конверт удаляется после подтверждения получения или через 30 дней;
- ничего не записывает о времени входа, IP-адресах, связях между пользователями;
- ограничивает частоту запросов: поиск пользователей, отправку и регистрации;
- при повторной отправке после обрыва связи не дублирует конверт благодаря клиентскому `cid`.

## Ключ сервера

У каждого ретранслятора свой ключ Ed25519, выведенный из его секрета (`secret.key` в папке данных или `SERVER_SECRET`); `serverId` — хэш открытого ключа.

- Клиент подключается с адресом `…/ws?c=<случайный вызов>`, сервер в `hello` подписывает `veil-server-proof-v1|<вызов>`. Подделать ответ, не имея ключа, нельзя, а записанный ответ не подходит к новому вызову.
- Клиент запоминает ключ при первом подключении (или берёт из приглашения `sk=`). Если потом сервер не может его подтвердить, клиент **не входит в аккаунт и не переподключается сам**: в Настройки → Сервер показан отпечаток нового ключа и кнопка «доверять». TLS этого не заменяет: адрес туннеля принадлежит публичному ретранслятору, а не серверу за ним.
- Каждый ответ «@имя → ключ» (`lookup`, `resolve`) сервер подписывает (`ssig`, `veil-user-v1|…`), клиент проверяет подпись запомненным ключом. Поддельный сервер в Wi-Fi с тем же `serverId`, но без ключа, не получит ни входа, ни возможности подсунуть ключ нового собеседника.
- Автопереподключение к серверу, сменившему адрес в Wi-Fi, срабатывает только для адресов домашней сети и только после подписи вызова тем же ключом.

## Сервер на своём компьютере в интернете

[`src/main/reach`](../src/main/reach), [`server/src/tunnel.ts`](../server/src/tunnel.ts).

- **Проброс порта** — UPnP-IGD (`@achingbrain/nat-port-mapper`), PCP (свой клиент, RFC 6887) и NAT-PMP. Внешний адрес роутера сверяется с публичным IP: серый адрес (10/8, 172.16/12, 192.168/16, 100.64/10) или несовпадение — это CGNAT, проброс снимается. Доступность проверяет публичный ретранслятор (`POST /reach`): запрос подписан ключом сервера, ретранслятор стучится **только на IP, с которого пришёл запрос**, на один порт, только `GET /health`, с таймаутом 5 с и не чаще 3 раз в час на ключ и IP. Ответ засчитывается, только если `/health` назвал тот же ключ. Указать чужой адрес нельзя, поэтому это не сканер портов.
- **Туннель.** Сервер на ПК открывает исходящее соединение `wss://<ретранслятор>/tunnel` и подписывает регистрацию (`veil-tunnel-register-v1|nonce|ключ ретранслятора`). Адрес `/t/<id>/ws`, где `id` — хэш ключа сервера, после перезапуска остаётся тем же. Подключения клиентов ретранслятор передаёт как виртуальные соединения; IP клиента приходит в кадре `t_open`, подписанном ключом ретранслятора, и сервер на ПК обслуживает соединение тем же кодом, что и обычный WebSocket, включая `hello`, подписанный ключом **сервера на ПК**. Лимиты задаются переменными окружения: туннелей на IP и всего, соединений на туннель, трафика в сутки, простоя. Каждые 5 минут идёт keepalive (бесплатный Render засыпает через 15 минут тишины), после обрыва — переподключение с экспоненциальной задержкой.
- **Что видит публичный ретранслятор:** то же, что и любой сервер Veil — кто подключён, к какому туннелю и сколько весят конверты. Содержимое — нет.
- **Регистрация только по приглашению** включается вместе с доступом из интернета. Одноразовый токен (16 случайных байт, 7 дней) лежит в ссылке `veil://` (`r=`), сервер хранит только его SHA-256. Владелец выпускает токены без ограничений, пользователи — до 5 в сутки.
- **`X-Forwarded-For`** учитывается только при `TRUST_PROXY=<число прокси>`, и берётся адрес, который добавил прокси (справа), — не то, что написал клиент. Встроенный сервер этот заголовок игнорирует; IP клиентов туннеля приходит в подписанном кадре.
- Пока компьютер спит, сообщения ждут у отправителей; по желанию Veil не даёт системе засыпать (`powerSaveBlocker`).

## «Избранное»

Чат с самим собой (`SAVED_ID` в [`src/core/types.ts`](../src/core/types.ts)). Его сообщения и файлы записываются только в зашифрованное хранилище на устройстве: движок не шифрует их для отправки и не ставит в очередь, а конверты, отправитель которых выдаёт себя за «Избранное», отбрасываются. При сохранении сообщения из другого чата файлы копируются, поэтому запись остаётся, даже если оригинал удалён или исчез по таймеру. Текст «Избранного», как и остальных чатов, входит в резервную копию для восстановления, зашифрованную паролем.

## Звонки

[`src/renderer/src/lib/calls.ts`](../src/renderer/src/lib/calls.ts): аудио- и видеозвонки на WebRTC.

- **Сигналы звонка** (предложение, ответ, завершение) идут как обычные сообщения Veil, зашифрованные сеансом Double Ratchet и sealed sender. Внутри предложения и ответа лежит SDP со всеми ICE-кандидатами и **отпечатком DTLS-сертификата** каждой стороны.
- **Звук** шифруется DTLS-SRTP. Ключи согласует DTLS-рукопожатие, а отпечатки сертификатов, которые оно проверяет, пришли через сквозное шифрование. Поэтому ни ретранслятор, ни STUN/TURN-сервер не могут подменить себя посередине и подслушать разговор: для этого им пришлось бы подделать сообщение внутри Double Ratchet.
- Предложение звонка отправляется только онлайн-собеседнику и не ставится в очередь, а задержавшееся дольше минуты отбрасывается: звонок, пришедший через час, звонить не будет. Сигнал завершения ставится в очередь, поэтому собеседник, который был не в сети, увидит «Пропущенный звонок».
- Звонки от заблокированных пользователей не доходят.
- **IP-адрес.** При прямом соединении собеседники видят IP-адреса друг друга, а публичный STUN-сервер (Google или Cloudflare, если ретранслятор не указал свой) видит ваш IP в момент звонка. Режим «Скрывать мой IP в звонках» разрешает только TURN-кандидаты (`iceTransportPolicy: relay`): собеседник видит адрес TURN-сервера, а TURN видит оба адреса, но не содержимое.
- Временные пароли TURN выдаёт ретранслятор после входа: `HMAC-SHA1(TURN_SECRET, срок:идентификатор)` по схеме TURN REST API, срок действия сутки.
- История звонков хранится только на устройстве, на сервер не отправляется.

### Видео и показ экрана

- Камера и экран идут по тому же DTLS-SRTP-соединению, что и голос, через те же STUN/TURN; «Скрывать мой IP» действует и на видео.
- В каждом звонке сразу согласуются два пустых видеоканала: камера и экран. Включение камеры или экрана только кладёт дорожку в канал (`replaceTrack`), без нового обмена SDP. Что включено, собеседник узнаёт из сигнала `media` — он тоже идёт внутри сквозного шифрования.
- Камера включается только по кнопке «Камера» или «С видео» и выключается сразу по кнопке или в конце звонка.
- **Показ экрана.** На Windows и Linux X11 Veil показывает свой список экранов и окон (миниатюры из `desktopCapturer`), и показывается только выбранное. На Wayland список окон приложению недоступен: экран или окно выбирается в системном окне портала xdg-desktop-portal (PipeWire).
- Пока вы показываете экран, Veil размывает всю переписку (Вуаль для всех чатов и «Избранного»), закрывает карточки уведомлений и не показывает новые, а также не играет звук сообщений. Звук компьютера не передаётся — только картинка.
- Если включена «Защита от скриншотов», на Windows окно Veil в показе экрана будет чёрным: так работает защита.

## Двухфакторная аутентификация

[`server/src/shared/totp.ts`](../server/src/shared/totp.ts) — TOTP по RFC 6238 (HMAC-SHA1, 6 цифр, шаг 30 секунд, допуск ±1 шаг), совместимый с Google Authenticator, Microsoft Authenticator и Authy.

- Секрет создаётся на устройстве и показывается QR-кодом. Он хранится в зашифрованном хранилище на устройстве и на сервере: серверу он нужен, чтобы проверять код при восстановлении по почте, отключении 2FA и удалении аккаунта.
- Сервер запоминает последний принятый шаг времени, поэтому один и тот же код нельзя использовать дважды.
- При разблокировке на своём устройстве код проверяется локально, до подключения к серверу. Это защищает от человека, который узнал пароль и сел за ваш компьютер. От вредоносной программы, которая уже скопировала хранилище и подсмотрела пароль, локальная проверка не защищает: секрет лежит в том же хранилище.

## Восстановление по почте

[`server/src/relay.ts`](../server/src/relay.ts), [`server/src/mailer.ts`](../server/src/mailer.ts), `startRecovery` / `restoreAccount` в [`src/core/messenger.ts`](../src/core/messenger.ts).

**Почта.** Сервер хранит не адрес, а `HMAC-SHA256(pepper, email)`, где `pepper` — 256-битный секрет сервера в файле `secret.key`. Адрес нужен ему только в момент отправки письма. По утёкшей базе без `secret.key` нельзя даже перебрать адреса по словарю. Почта привязывается только после ввода кода из письма.

**Резервная копия.** Клиент шифрует аккаунт, контакты, настройки и до 3000 последних сообщений каждого чата (исчезающие сообщения в копию не попадают):

```
key    = scrypt(пароль, отдельная соль, N = 2¹⁷, r = 8, p = 1)
backup = XChaCha20-Poly1305(key, gzip(JSON), AD = "veil-backup-v1")
```

Копия обновляется не чаще раза в 10 минут и при каждом входе, если она старше 6 часов. Сервер видит только её размер и дату. Состояния сеансов Double Ratchet в копию **не входят**: после восстановления устройство заново устанавливает сеансы со всеми контактами, чтобы не переиспользовать ключи сообщений.

**Восстановление.**

1. `recover_start` (username + почта) — сервер отвечает одинаково, совпала почта или нет, поэтому так нельзя узнать, какая почта у аккаунта. Писем не больше 5 в час на IP и на аккаунт.
2. `recover_finish` — 6-значный код (живёт 15 минут, 5 попыток) и, если включена 2FA, код из приложения. Сервер выдаёт зашифрованную копию и одноразовый токен на 30 минут.
3. Копия расшифровывается паролем на устройстве. Если пароль забыт, токен позволяет зарегистрировать на то же имя **новые** ключи: старую переписку прочитать нельзя, а у собеседников меняется код безопасности.

Таким образом, доступ к почте сам по себе не даёт ни переписки (нужен пароль), ни захвата имени при включённой 2FA. Без 2FA человек с доступом к почте может перерегистрировать ваше имя на свои ключи — собеседники увидят смену кода безопасности. Поэтому вместе с почтой стоит включить 2FA.

## Обновления

[`src/main/updater.ts`](../src/main/updater.ts) использует electron-updater: установщик Windows и AppImage скачивают обновление из GitHub Releases, проверяют SHA-512 из `latest.yml` и ставят его после подтверждения. Остальные сборки только сообщают о новой версии и открывают страницу релиза. Сборки не подписаны платным сертификатом, поэтому подлинность обновления держится на HTTPS и доступе к репозиторию.

## Хранение на устройстве

[`src/core/crypto/vault.ts`](../src/core/crypto/vault.ts), [`src/core/storage.ts`](../src/core/storage.ts):

- случайный 256-битный ключ данных шифрует каждую запись (XChaCha20-Poly1305 с именем записи в AD, чтобы записи нельзя было переставить);
- сам ключ данных зашифрован ключом, выведенным из пароля через scrypt. Смена пароля перешифровывает только его;
- при блокировке ключи удаляются из памяти (насколько это возможно в JavaScript), а запись на диск запрещается;
- имена файлов на диске представлены в hex и ничего не говорят о содержимом.

## Оболочка Electron

[`src/main/index.ts`](../src/main/index.ts): `contextIsolation`, `sandbox`, без `nodeIntegration`, строгая Content-Security-Policy, запрет новых окон и навигации, проверка отправителя каждого IPC-вызова. Из разрешений выдаются только уведомления, запись в буфер обмена, микрофон и камера (голосовые, звонки, видео и сканирование QR-кода приглашения; включаются только вашим действием, на macOS — ещё и с разрешения системы); геолокация, MIDI, USB и остальное запрещены. Ссылки открываются во внешнем браузере.

Всплывающие уведомления ([`src/main/notifications.ts`](../src/main/notifications.ts)) — отдельные окна без доступа к Node.js и к хранилищу. Они получают только то, что разрешено показывать настройкой «Уведомления»: по умолчанию без текста сообщения.

## Группы — Sender Keys

[`src/core/crypto/sender-keys.ts`](../src/core/crypto/sender-keys.ts), [`src/core/groups.ts`](../src/core/groups.ts).

**Почему Sender Keys, а не MLS.** Sender Keys (схема Signal и WhatsApp) работают поверх того, что в Veil уже есть: парных сеансов X3DH + Double Ratchet и конвертов sealed sender, и ничего не требуют от ретранслятора. MLS нужна служба доставки, которая упорядочивает изменения группы для всех участников, — это новая роль сервера и второй стек протоколов ради выигрыша (дешёвая смена состава в очень больших группах), который группам до 50 человек не нужен.

**Как устроено.**

- У каждого участника для каждой группы своя цепочка: ключ цепочки `CK` и пара ключей подписи Ed25519. Ключ сообщения `MK = HMAC-SHA256(CK, 0x01)`, следующая цепочка `CK' = HMAC-SHA256(CK, 0x02)`; ключ сообщения используется один раз.
- Сообщение шифруется **один раз** (XChaCha20-Poly1305, AD = группа | отправитель | цепочка | номер) и подписывается ключом подписи цепочки. Каждый участник получает тот же шифротекст в своём конверте sealed sender — сервер видит только конверты, как в личных чатах.
- Ключ цепочки и открытый ключ подписи каждый отправляет каждому участнику **по личному сквозному каналу** (Double Ratchet). Подпись не даёт одному участнику писать от имени другого, хотя ключ цепочки у них общий.
- Состав группы, роли и название рассылаются по личным каналам. Сервера-арбитра нет: каждый участник проверяет каждое изменение по одним правилам. Владелец может всё, включая роли и передачу владения; админ — переименовать, добавлять и удалять обычных участников; участник — писать и выйти. Изменение от того, у кого нет прав, или со старым номером версии отбрасывается.
- Когда кто-то удалён или вышел, **все оставшиеся начинают новые цепочки**: новые сообщения он не прочитает. Новый участник видит только сообщения после добавления.
- Если ключ участника потерялся (восстановление из копии), приложение само попросит его заново; сообщения, отправленные в промежутке, не расшифруются.
- «Щит группы» показывает, у скольких участников ключи сверены — сверка идёт в личном чате с каждым.

| Угроза | Защищает? |
|---|---|
| Сервер читает сообщения, название или состав группы | Нет: всё внутри сквозного шифрования, сервер видит только отдельные конверты. |
| Сервер добавляет в группу своего человека | Нет: состав меняют только владелец или админ, и каждое изменение проверяет каждый участник. |
| Участник пишет от имени другого | Нет: сообщения подписаны ключом отправителя. |
| Удалённый участник читает новые сообщения | Нет: все сменили цепочки. |
| Сервер видит, что конверты пришли нескольким людям одновременно | Да, это метаданные доставки — как и в личных чатах. |
| Подмена ключа участника при первом контакте | Сверяйте код безопасности с каждым участником; «Щит группы» показывает, у скольких это сделано. |

Чего в группах пока нет: звонков, реакций, исчезающих сообщений, капсул времени, фото «на один просмотр», отчётов о прочтении и «удалить у всех».

## Поиск по всей переписке

[`src/core/search.ts`](../src/core/search.ts). Поиск идёт только по этому устройству и ничего не отправляет на сервер (это проверяет тест). Отдельного индекса на диске нет: пока Veil разблокирован, переписка и так расшифрована в памяти, а на диске лежит только зашифрованное хранилище, поэтому SQLCipher не понадобился. Нормализованный текст для поиска живёт в памяти рядом с сообщениями и исчезает при блокировке. Никогда не находятся: пароли из «Избранного» (только их названия), фото и видео «на один просмотр», закрытые капсулы времени. Скрытые чаты в результатах появляются, только пока они открыты.

## Голосовые в текст

[`src/renderer/src/lib/transcribe.worker.ts`](../src/renderer/src/lib/transcribe.worker.ts), [`src/main/models.ts`](../src/main/models.ts).

- Распознавание идёт на этом компьютере: модель Whisper работает в отдельном потоке (Web Worker) через ONNX Runtime (WebAssembly), который поставляется внутри Veil. Голосовые никуда не отправляются, интернет для распознавания не нужен.
- Модель скачивается **только после согласия**, один раз, с `huggingface.co` (Xenova/whisper-tiny, -base или -small, квантованные: ≈ 40, 80 или 250 МБ) и хранится в папке данных Veil. Hugging Face видит только, что с вашего IP скачали общедоступную модель. Удалить модель можно в Настройки → Аудио.
- Модель отдаётся распознавателю через внутреннюю схему `veil-model://`, которая открывает только файлы модели из этой папки. В политике безопасности страницы разрешены `'wasm-unsafe-eval'` (для WebAssembly) и `veil-model:`; загрузка кода из интернета по-прежнему запрещена.
- Текст хранится рядом с голосовым в зашифрованном хранилище этого устройства и **никому не отправляется**: у собеседника его нет, пока он не расшифрует голосовое сам. Подпись под текстом: «Текст: на устройстве».
- В браузерной версии расшифровки нет: там негде хранить модель отдельно от сайта.

## Мост: перенос на другой ПК — схема угроз

[`src/core/bridge.ts`](../src/core/bridge.ts). Перенос **перемещает** аккаунт: после него Veil на старом ПК очищается, потому что сеансы Double Ratchet нельзя безопасно вести с двух устройств одновременно.

**Что защищаем.** Ключи личности, сеансы, контакты, переписку, «Избранное» и файлы — всё, что лежит в хранилище.

**Канал.**

```
старый ПК: эфемерная пара X25519 (a), случайный код из 8 символов (40 бит), показан на экране
новый ПК:  эфемерная пара X25519 (b), код вводит человек
shared     = X25519(a, B) = X25519(b, A)
transcript = SHA-256("veil-bridge-v1" ‖ A ‖ B ‖ nonce_old ‖ nonce_new)
ключи      = HKDF-SHA256(shared, salt = transcript, info = "veil-bridge-v1|" ‖ код) → два ключа, по одному на направление
SAS        = 6 цифр из HKDF-SHA256(shared, salt = transcript, info = "veil-bridge-sas")
```

Новый ПК доказывает знание кода HMAC-подтверждением на своём ключе. Старый ПК отправляет данные, только когда подтверждение верно **и** человек нажал «Цифры совпадают» после сверки шести цифр на обоих экранах. Данные идут кадрами XChaCha20-Poly1305 с номером кадра в AD: кадры нельзя переставить, повторить или подменить.

| Угроза | Что происходит |
|---|---|
| Кто-то в той же сети подслушивает | Видит только шифр. Без эфемерных ключей и кода не расшифровать. |
| Кто-то в сети встаёт посередине | Без кода он не может вывести ключи; даже подобрав код, получит **другие** шесть цифр — человек увидит расхождение. После трёх неверных попыток старый ПК создаёт новый код. |
| Кто-то подсмотрел код на экране | Ему ещё нужно оказаться в сети раньше вас и совпасть по шести цифрам. Сверяйте цифры. |
| Перебор кода по перехваченному подтверждению | Возможен на мощном оборудовании за часы — дольше, чем живёт сессия (10 минут); и всё равно упирается в сверку цифр. Это слабее настоящего PAKE: проверенной реализации PAKE в используемых библиотеках нет, а придумывать свою мы не стали. |
| Обнаружение в сети (mDNS) | В объявлении — только имя компьютера и порт. Код, ключи и имя пользователя в сеть не уходят. |
| Перенос через сервер (нет общей сети) | Ретранслятор соединяет два ПК в «комнате»: её номер (4 символа) входит в показанный код из 12 символов, а секретная часть — нет. Сервер видит только шифр, его размер и время. Предупреждение показывается до начала. |
| Старый ПК остался с данными | После подтверждения «перенос завершён» старый ПК стирает хранилище и ключ быстрого входа. |

**Раздел «Устройства».** Каждая установка получает случайный номер устройства; ретранслятор хранит для аккаунта до 10 номеров с датой последнего входа и названием ПК, **зашифрованным ключом, который знает только ваш аккаунт**. Это новые метаданные — сервер узнаёт, со скольких ПК и когда вы входили (время входов он и так видит). «Отвязать» запрещает ретранслятору принимать вход с этого номера: так забытый или проданный ПК перестанет получать ваши сообщения. Если ключи украдены (скопировано хранилище и пароль), отвязка не поможет: злоумышленник может назваться новым устройством — нужен новый аккаунт.

## Аварийный пароль — схема угроз

[`src/core/crypto/vault.ts`](../src/core/crypto/vault.ts), `unlock` в [`src/core/messenger.ts`](../src/core/messenger.ts).

**Ситуация.** Вас заставляют открыть Veil при другом человеке. Вы вводите аварийный пароль — открывается пустой Veil с вашим именем: ни контактов, ни переписки, ни «Избранного».

**Как устроено.**

- В метаданных хранилища всегда есть **два** слота с ключом: настоящий и аварийный. Если аварийный пароль не включён, второй слот заполнен случайными байтами того же размера, поэтому по файлу нельзя понять, включён ли он.
- Оба слота закрыты ключом из одного и того же scrypt (одна соль): при вводе любого пароля выполняется ровно одно вычисление scrypt и две попытки расшифровки. Время входа одинаковое, экран один и тот же.
- Пустой Veil — отдельное зашифрованное хранилище со своим ключом, свежими ключами личности и вашим именем. Он **не подключается к серверу** и показывает «В сети»: так на сервере не появляется второй аккаунт, а настоящие сообщения не уходят в пустой Veil и ждут на сервере.
- «Стереть всё при вводе» (включается с двойным подтверждением): ввод аварийного пароля сначала удаляет настоящее хранилище и ключ быстрого входа, затем открывает пустой Veil. Отменить нельзя.

| Угроза | Защищает? |
|---|---|
| Человек смотрит на экран, листает чаты и настройки | Да: пустой Veil выглядит как обычный. |
| Человек замеряет время входа | Да: одно вычисление scrypt в обоих случаях. |
| Человек знает про функцию и требует «второй пароль» | Нет. Помогает только «Стереть всё при вводе». |
| Человек пытается кому-то написать из пустого Veil | Поиск контактов отвечает «не найден», сообщение не уйдёт. Внимательный человек может это заметить. |
| Экспертиза диска | Нет: видно, что на диске больше зашифрованных записей, чем показывает пустой Veil. Прочитать их без настоящего пароля нельзя. |
| Собеседники | Видят, что вы не в сети: настоящий аккаунт не подключён. |
| Быстрый вход по PIN | PIN открывает только настоящий Veil. При угрозе принуждения быстрый вход лучше выключить. |

## Приглашение veil:// — схема угроз

[`src/core/invite.ts`](../src/core/invite.ts), `createInvite` / `acceptInvite` в [`src/core/messenger.ts`](../src/core/messenger.ts).

**Что внутри ссылки.** `veil://add/<имя>?k=<ключ>&s=<сервер>&t=<токен>`. `k` — сам ключ личности (Ed25519, он же идентификатор аккаунта), ничего нового не вычисляется. `t` — 16 случайных байт, живёт 7 дней и срабатывает один раз.

**Как устроено.**

- Тот, кто открыл ссылку, запрашивает ключ у сервера и сравнивает с ключом из ссылки **до того**, как что-то сохранить. Не совпало — контакт не добавляется, в журнал безопасности пишется «ключ не совпал с приглашением».
- Совпало — контакт сразу «Сверен приглашением»: ключ пришёл не от сервера, а от человека.
- Токен уходит обратно в первом сообщении, внутри сквозного шифрования. Прочитать его может только владелец настоящего ключа, а знает его только тот, у кого была ссылка, — поэтому у пригласившего новый контакт тоже становится сверенным. Использованный или просроченный токен никого не сверяет.

| Угроза | Защищает? |
|---|---|
| Сервер подменяет ключ пригласившего | Да: ключ из ссылки не совпадёт. |
| Сервер подменяет ключ того, кто открыл ссылку | Да: без токена пригласивший его не сверит, а токен идёт внутри сеанса с настоящим ключом. |
| Сервер читает токен | Нет: токен идёт только в зашифрованном сообщении (проверяется тестом «сервер видит только шифр»). |
| Ссылку переслали третьему человеку | Сверен будет тот, кто открыл её первым. Передавайте ссылку лично или показывайте QR-код. |
| Кто-то увидел ссылку на экране | Узнает только имя и открытый ключ — это не секрет. Токен одноразовый. |

## От чего Veil не защищает

- **Заражённое устройство.** Вредоносная программа на вашем компьютере видит то же, что и вы.
- **Метаданные доставки.** Сервер видит, кому адресован конверт, когда он пришёл и с какого IP. Для защиты IP используйте VPN или Tor.
- **IP-адрес в звонках** без TURN виден собеседнику.
- **Подмена ключей при первом контакте**, если вы не сверили код безопасности. Сверяйте его — или добавляйтесь по приглашению veil:// при встрече.
- **Перехват почты без 2FA.** Тот, кто читает вашу почту, может восстановить на себя имя `@username` (но не переписку). Включайте 2FA.
- **Слабый пароль.** scrypt замедляет перебор, но не спасает пароль `123456`.
- Независимого аудита кода мессенджера не было.
